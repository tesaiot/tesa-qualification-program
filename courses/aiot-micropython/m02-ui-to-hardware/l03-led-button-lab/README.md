# บทเรียน 2.3 — ลงมือทำ: ไฟวิ่งกับปุ่ม แล้วส่งขึ้น broker

> โมดูล 2 — จากจอสู่ฮาร์ดแวร์ · สไลด์: [slides.md](slides.md) · [ภาพรวมโมดูล](../README.md) · [หน้าหลักสูตร](../../README.md)

เติมช่องว่างหกจุดจนได้ไฟวิ่งครบทุกดวงที่ปรับจังหวะได้กับปุ่มที่นับตรงสิบครั้งสิบ แล้วต่อยอดให้การกดปุ่มหนึ่งครั้งไปโผล่บนหน้าเว็บผ่าน broker โดยเขียนรอบข้อจำกัดจริงของเฟิร์มแวร์

## เป้าหมาย

เมื่อจบบทเรียนนี้ คุณจะ:

1. เติมช่องว่างหกจุดใน practice/s03_led_button.py จนผ่าน MVP คือไฟวิ่งครบทุกดวงที่ gpio.num_leds() บอก แก้ STEP_MS อย่างน้อยสองค่าแล้วจังหวะเปลี่ยนตาม กดปุ่มผู้ใช้สิบครั้งตัวเลขขึ้นสิบพอดี และจบโปรแกรมด้วยไฟดับทุกดวงพร้อมบรรทัดสรุปสีเขียว
2. จับคู่อาการที่เจอบ่อยกับสาเหตุและวิธีแก้ได้ (เลขขึ้นทีละ 3–5 ขึ้นทีละ 2 ไม่ขึ้นเลย ไฟค้างดวงเดียว ไฟติดสองดวง) และอธิบายให้ผู้สอนฟังได้ว่าถ้าเอาโค้ดกันเด้งออกจะเกิดอะไรและเพราะอะไร
3. รัน 07_button_to_broker.py ด้วยชื่อทีมของตัวเองจนหน้า my_first_reader.html เห็น telemetry ทุก 2 วินาทีและ event ทันทีที่กด แล้วอธิบายได้ว่า retain ที่เป็น false เสมอ กล่องรับช่องเดียว OSError ตอนสายหลุด และ client_id ที่ซ้ำไม่ได้ ทำให้โค้ดต้องหน้าตาแบบนี้อย่างไร
4. อธิบายได้ว่าทำไมเกมกดเร็วทั้งห้องจับเวลาบนบอร์ดแทนลำดับที่ผลมาถึง และทำไมจดเวลาตอนขาเริ่มเปลี่ยนแทนตอนที่กันเด้งยืนยัน

## แนวคิด

**MVP ของชุดบทเรียน 2.1–2.3** คือไฟวิ่งครบทุกดวงของบอร์ดที่ปรับจังหวะได้ กับปุ่มผู้ใช้ (เรียกด้วยชื่อจาก `.name()`)
ที่นับครั้งขึ้นจอ ข้อที่ยากที่สุดไม่ใช่การทำให้ได้ แต่คือ **อธิบายได้** ว่าถ้าเอาโค้ดกันเด้งออกจะเกิดอะไร
และสังเกตว่ากับดักสามข้อแรกในตารางของสไลด์เป็นเรื่อง *ตรรกะเวลา* ไม่ใช่ไวยากรณ์ ซึ่งเป็นลักษณะเฉพาะของงานฝังตัว

ไฟล์เฉลยวางค่าที่ปรับบ่อยสี่ตัวไว้บนสุดเป็น **หน้าปัดของโปรแกรม** (`STEP_MS` `DEBOUNCE_MS` `POLL_MS` `RUN_MS`)
เกณฑ์ "ปรับจังหวะได้" จึงเหลือแค่แก้ `STEP_MS` ตัวเดียว ในลูปมีสี่จังหวะที่ไม่เท่ากัน: ปุ่มถูกถามทุก 5 ms ไฟขยับทุก 150 ms
จอเดินทุก `UI_MS` = 100 ms (เรียก `ui.poll()` ทุกรอบลูปคือการยิง IPC ข้ามคอร์ 200 ครั้งต่อวินาทีเพื่อรอนิ้วที่มาวินาทีละครั้ง)
และตัวเลขที่คนต้องอ่านเขียนใหม่ไม่เกินวินาทีละครั้ง ทั้งหมดใช้ `now = time.ticks_ms()` ค่าเดียวต่อรอบ
และ `time.sleep_ms(POLL_MS)` ท้ายลูปคือจุดเดียวที่โปรแกรมยอมพัก แผงบนจอสร้างครั้งเดียวก่อนเข้าลูป
ปุ่ม "เดินไฟวิ่ง" กับ "หยุดไฟวิ่ง" แยกกันโดยตั้งใจ และกล่องยืนยันถูกสร้างแล้วซ่อนไว้ตั้งแต่ต้น

ห้าท่าเรียงแบบ **bring-up ทีละชั้น**: ถามบอร์ด → ดับให้หมด → ไฟวิ่ง (งานที่ไม่พึ่งอินพุตจากใคร ถ้าวิ่งได้แปลว่าโครงลูปกับนาฬิกาถูก)
→ ปุ่ม (ถ้าพังตอนนี้ รู้แน่ว่าพังที่ปุ่มหรือกันเด้ง) → ปิดท้าย การเติมช่องว่างก็ทำตามลำดับเดียวกัน

ต่อขึ้น broker ได้ด้วยการเพิ่มของแค่สามจุดในลูปเดิม: `send()` สองจุดกับ `get_message()` หนึ่งจุด ทีมละสามหัวข้อ
`bento-aiot/<ทีม>/event` (ทันทีที่กด ผ่านกันเด้งแล้ว) `…/telemetry` (ทุก 2 วินาที) และ `…/cmd` (เว็บสั่งบอร์ด)
ทุกใบมี `n` ที่เดินต่อกัน อีกฝั่งเห็นเลขกระโดดก็รู้ว่ามีใบหาย ข้อจำกัดของเฟิร์มแวร์สี่ข้อคือข้อมูลออกแบบ ไม่ใช่ข้อตำหนิ:
`publish()` ส่ง retain = false เสมอ จึงต้องส่ง telemetry ซ้ำทุก 2 วินาที · `get_message()` เป็นกล่องช่องเดียว ใบใหม่ทับใบเก่า
จึงต้องหยิบทุกรอบลูป · `publish()` ตอนสายหลุดโยน `OSError` ซึ่ง `send()` ดักไว้แล้วคืน `False` ให้ลูปหยุดอย่างสุภาพ
· ไม่ต่อใหม่ให้เองและ `clean_session` เป็นจริงเสมอ จึงถาม `is_connected()` ทุกรอบ และ client_id ซ้ำกันไม่ได้
ใครต่อทีหลังจะเตะคนก่อนหลุด ไฟล์ 07 จึงรันได้บอร์ดเดียวต่อทีม

## ฝึกเติม

ไฟล์ฝึกมีช่องว่าง `# เติม:` หกจุด ระวังการเยื้องบรรทัด เพราะสามจุดกลางอยู่คนละชั้นกัน ถ้าเยื้องผิด Python จะเอาโค้ดไปไว้ผิดเงื่อนไข

- จุด 1: `gpio.led(i).off()` ในลูปดับไฟก่อนเริ่ม
- จุด 2: `led_index = (led_index + 1) % NUM_LEDS` ระหว่างดับดวงเดิมกับจุดดวงใหม่
- จุด 3: `raw = btn.is_pressed()` ต้นท่าที่ 4
- จุด 4: `last_change = now` ในกิ่งที่ค่าดิบเพิ่งขยับ
- จุด 5: `count += 1` ใต้ `if stable:`
- จุด 6: บรรทัด `lcd.print` สรุปสีเขียวหลังลูป

เติมจุด 1–2 แล้วรันก่อน ไฟต้องวิ่งครบทุกดวง (ตอนนี้กดปุ่มแล้วเลขยังไม่ขยับ เพราะ `raw` ถูกตั้งเป็น `False` ไว้ให้ไฟล์รันได้)
จากนั้นเติมจุด 3–5 แล้วกดสิบครั้ง ต้องได้สิบพอดี สุดท้ายเติมจุด 6 พอไฟวิ่งได้แล้วปุ่มพัง เรารู้ทันทีว่าปัญหาไม่ได้อยู่ที่ไฟ

## เช็กความเข้าใจ

คำถามชุดเดียวกันอยู่ใน [quiz.yaml](quiz.yaml) สำหรับระบบที่ตรวจอัตโนมัติ

1. ทีมเติมเฉพาะจุด 1–2 ในไฟล์ฝึกแล้วกด Program to Device จะเห็นอะไร *(เลือกหนึ่งข้อ · เป้าหมายข้อ 1)*
   - ก) ไฟวิ่งครบทุกดวง แต่กดปุ่มแล้วตัวนับไม่ขยับ เพราะ raw ยังเป็น False ที่ตั้งไว้ให้ไฟล์รันได้
   - ข) โปรแกรมหยุดทันทีด้วย NameError เพราะยังไม่มีบรรทัด raw = btn.is_pressed()
   - ค) ไฟไม่วิ่ง เพราะลูปต้องรอให้กดปุ่มก่อนจึงจะขยับไฟ
   - ง) ไฟวิ่งและนับปุ่มได้ แต่นับเกินจริง เพราะยังไม่ได้เติมส่วนกันเด้ง

   <details><summary>เฉลย</summary>

   **ก** — ไฟวิ่งเป็นงานที่ไม่พึ่งอินพุตจากใคร จึงทำงานได้ทันทีหลังจุด 1–2 ส่วน raw ถูกตั้งเป็น False ไว้ก่อน ไฟล์จึงไม่พัง แต่ปุ่มยังไม่ถูกอ่าน การเติมทีละกลุ่มแบบนี้ทำให้รู้ว่าถ้าปุ่มพังตอนหลัง ปัญหาไม่ได้อยู่ที่ไฟ

   </details>

2. อาการคู่กับสาเหตุข้อใดถูกต้อง เลือกทุกข้อที่ถูก *(เลือกได้หลายข้อ · เป้าหมายข้อ 2)*
   - ก) กดหนึ่งครั้ง เลขขึ้น 3–5 ← ยังไม่ได้กันเด้ง หรือ DEBOUNCE_MS น้อยเกิน
   - ข) กดแล้วเลขไม่ขึ้นเลย ← มี sleep_ms ยาวในลูป ปุ่มหลุดตอนหลับ
   - ค) ไฟติดพร้อมกันสองดวง ← จุดดวงใหม่ก่อนดับดวงเดิม
   - ง) จอไม่ขึ้นตัวเลขแต่ไฟวิ่งปกติ ← DEBOUNCE_MS สูงเกินไป
   - จ) ไฟไม่วิ่ง ค้างดวงเดียว ← ลืม if stable

   <details><summary>เฉลย</summary>

   **ก, ข, ค** — สามข้อแรกตรงกับตารางกับดัก ส่วนจอไม่ขึ้นตัวเลขทั้งที่ไฟวิ่งเกิดจากไม่ได้เปิดหน้า Playground ไว้ และไฟค้างดวงเดียวเกิดจาก last_step = now อยู่นอก if ส่วนการลืม if stable ทำให้เลขขึ้นทีละสอง

   </details>

3. ทำไม 07_button_to_broker.py ส่ง telemetry ซ้ำทุก 2 วินาที ทั้งที่สถานะอาจไม่ได้เปลี่ยนเลย *(เลือกหนึ่งข้อ · เป้าหมายข้อ 3)*
   - ก) เพราะ publish() ของเฟิร์มแวร์นี้ส่ง retain = false เสมอ broker ไม่เก็บใบล่าสุดไว้ หน้าเว็บที่เปิดทีหลังจึงต้องรอใบถัดไป
   - ข) เพราะ broker สาธารณะตัดการเชื่อมต่อถ้าไม่มีข้อมูลเข้าภายใน 2 วินาที
   - ค) เพราะกล่องรับของบอร์ดมีช่องเดียว ต้องส่งออกก่อนจึงจะรับได้
   - ง) เพราะ event อาจส่งซ้ำ จึงต้องมี telemetry ไว้ลบใบที่ซ้ำ

   <details><summary>เฉลย</summary>

   **ก** — publish() ส่ง retain = false เสมอแม้ docstring จะเขียนว่ารับ retain= ถ้าส่งเฉพาะตอนเปลี่ยน หน้าเว็บที่เปิดทีหลังจะจอว่าง การส่งซ้ำทุก 2 วินาทีทำให้หน้าเว็บที่เปิดช้าที่สุดก็ตามทันภายใน 2 วินาที

   </details>

4. ข้อใดถูกต้องเกี่ยวกับการเขียน 07_button_to_broker.py รอบข้อจำกัดของเฟิร์มแวร์ เลือกทุกข้อที่ถูก *(เลือกได้หลายข้อ · เป้าหมายข้อ 3)*
   - ก) ต้องกันเด้งก่อน publish ไม่งั้นกดหนึ่งครั้งกลายเป็นหลายใบบน broker และคนที่อ่านอีกฝั่งแยกไม่ออกว่าใบไหนคือการกดจริง
   - ข) ส่งสถานะไฟจากตัวแปร leds ที่ handle() จดไว้ ไม่ใช่จาก gpio.led(i).value()
   - ค) หยิบ get_message() ทุกรอบลูป เพราะกล่องรับมีช่องเดียว ใบใหม่ทับใบเก่า
   - ง) สองคนในทีมรันไฟล์ 07 ด้วย TEAM เดียวกันบนสองบอร์ดพร้อมกันได้ เพราะ broker แยกให้เอง
   - จ) ถ้าสายหลุด publish() คืน False ให้เองอยู่แล้ว ไม่ต้องดักอะไร

   <details><summary>เฉลย</summary>

   **ก, ข, ค** — client_id ซ้ำกันไม่ได้ ใครต่อทีหลังจะเตะคนก่อนหลุด ไฟล์ 07 ใช้ bento-aiot- ต่อด้วยชื่อทีม จึงรันได้บอร์ดเดียวต่อทีม และ publish() ตอนสายหลุดโยน OSError ไม่ได้คืน False จึงต้องให้ send() ดักไว้

   </details>

5. ข้อใดถูกต้องเกี่ยวกับการจับเวลาในเกมกดเร็วทั้งห้อง (08_class_race.py) เลือกทุกข้อที่ถูก *(เลือกได้หลายข้อ · เป้าหมายข้อ 4)*
   - ก) ทีมที่ผลขึ้นจอหน้าห้องก่อนอาจไม่ใช่ทีมที่เร็วที่สุด เพราะแต่ละบอร์ดสุ่มเวลารอเอง และข้อความเดินทางใช้เวลาไม่เท่ากัน
   - ข) บอร์ดจดเวลาตอนขาเริ่มเปลี่ยน แล้วค่อยใช้เวลานั้นเมื่อกันเด้งยืนยันว่าเป็นการกดจริง
   - ค) ถ้าจับเวลาตอนที่กันเด้งยืนยัน ทุกทีมจะได้เวลาเร็วกว่าจริง 40 ms
   - ง) กดเร็วกว่า 100 ms หลังไฟติดถือเป็นสถิติที่ดีที่สุดของรอบ

   <details><summary>เฉลย</summary>

   **ก, ข** — เราวัดบนบอร์ดระหว่างหลอดของมันเองกับปุ่มของมันเอง ทางเดินของข้อความจึงไม่อยู่ในตัวเลข กันเด้ง 40 ms ทำให้บอร์ดเชื่อช้ากว่านิ้ว ถ้าจับเวลาตอนเชื่อทุกทีมจะช้าเกินจริง และเร็วกว่า 100 ms นับเป็นออกตัวก่อน

   </details>
